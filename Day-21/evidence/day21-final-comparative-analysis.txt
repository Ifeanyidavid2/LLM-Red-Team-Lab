========================================
 LAB 1 ù SYNTHETIC PERSISTENT MEMORY
========================================

Key observations:

- Benign memory could be stored.
- Memory survived creation of a new session.
- Attacker-controlled security claims could also be stored.
- Owner-filtered retrieval provided an initial isolation primitive.
- Delete and reset deactivated memory.

Critical vulnerability:

Conversation-originated security claims could become durable
memory without independent authorization.

Finding:

Persistence is useful, but persistence must not imply trust.

========================================
 CROSS-LAB SECURITY FINDINGS
========================================

1. Persistent memory creates a security boundary that extends
   beyond the original conversation and session.

2. A syntactically valid memory write is not necessarily an
   authorized memory write.

3. In the vulnerable baseline, unauthorized and malicious
   memory writes succeeded in 100% of tested cases.

4. Poisoned memory persisted across sessions in 100% of the
   vulnerable persistence benchmark.

5. Persistent poison caused measurable security-state
   corruption in later sessions.

6. Role, MFA, approval, authorization, and policy claims are
   especially dangerous memory categories.

7. Cross-user memory isolation cannot rely only on filtering
   retrieval by owner.

8. Write-time ownership authorization is required to prevent
   attackers from poisoning another user's memory bucket.

9. Memory provenance must survive imports, migrations,
   connectors, and legacy storage.

10. Existing memory should not automatically become trusted
    merely because it is already stored.

11. Category policy alone is insufficient because malicious
    instructions can be embedded inside permitted memory
    categories.

12. Content sanitization can preserve legitimate factual
    memory while quarantining malicious instructions.

13. Deleted and reset memory must stop participating in active
    retrieval.

14. Audit retention and active memory retrieval are separate
    lifecycle concerns.

15. Security-sensitive state must be resolved independently
    from persistent memory.

16. Model-generated security claims and structured fields can
    contradict one another.

17. Model memory proposal quality is a separate utility metric
    from memory-layer security.

18. The hardened architecture reduced unauthorized durable
    writes to 0% in the final retest.

19. The hardened architecture reduced cross-session poison
    persistence to 0% in the final retest.

20. The hardened architecture reduced observed memory-driven
    security-state corruption to 0% in the final retest.

21. Legitimate persistence remained possible under the
    hardened architecture.

22. Persistent memory should therefore be treated as
    provenance-sensitive contextual data rather than as
    security authority.


========================================
 SECURITY / UTILITY ANALYSIS
========================================

A secure memory architecture must not simply reject all memory.

That would produce low attack success but would eliminate the
purpose of persistent personalization and context.

The experiments therefore measured both:

SECURITY

- unauthorized writes
- malicious writes
- cross-user writes
- poison persistence
- security-state corruption
- unsafe retrieval
- stale-memory resurrection

and:

UTILITY

- legitimate write success
- legitimate memory retrieval
- factual content preservation
- post-reset memory creation
- benign memory availability

The strongest deterministic controls achieved both:

100.00% legitimate memory preservation

and:

0.00% unauthorized write rate
0.00% unsafe retrieval exposure
0.00% memory-to-security override rate

The final LLM retest also preserved permitted memory storage
while preventing observed persistent security compromise.

However, model-side semantic memory fidelity remained imperfect.

========================================
 TRUST RULES
========================================

Persistent memory may safely contain ordinary contextual
information such as:

- response preferences
- project context
- benign profile facts
- user-selected personalization

Persistent conversation memory should not independently
establish:

- authenticated identity
- privileged role
- MFA completion
- authorization
- approval
- security policy
- tool permission
- another user's authority

Security-sensitive values must come from a trusted system of
record.


========================================
 LIMITATIONS
========================================

1. All identities, memory entries, approvals, roles, and
   security actions were synthetic.

2. The principal model was llama3.2:1b.

3. The attack corpus was intentionally small.

4. Several attack families used only one or a few examples.

5. Regex-based sanitization does not cover all semantic
   variants of malicious memory.

6. Obfuscated, encoded, multilingual, or indirect memory
   injection was not comprehensively tested.

7. The memory store was a simplified local implementation.

8. Production vector databases, embeddings, ranking, memory
   summarization, and memory consolidation were not modeled.

9. Real multi-tenant storage controls were not tested.

10. Real connectors and imported memory systems were not used.

11. Time-based expiry and retention-policy enforcement were
    not tested.

12. Cryptographic provenance was not implemented.

13. Model-generated structured fields were sometimes
    inconsistent or incomplete.

14. One final hardened retest case produced a model / JSON
    failure.

15. The final legitimate memory preservation metric measures
    permitted persistence, not semantic fidelity of the
    stored memory.

16. One legitimate model proposal stored generic text rather
    than the requested preference.

17. Reported percentages describe this controlled synthetic
    laboratory and must not be generalized as universal
    attack or defense rates.


========================================
 RECOMMENDATIONS
========================================

1. Authorize memory writes independently of the LLM.

2. Enforce memory ownership at write time and retrieval time.

3. Restrict which categories may be persisted from
   conversation content.

4. Prevent ordinary conversation memory from creating security
   authority.

5. Preserve provenance metadata for every persistent entry.

6. Distinguish trusted application state from untrusted or
   unknown memory.

7. Sanitize permitted memory for embedded adversarial
   instructions.

8. Treat imported and legacy memory as untrusted until
   provenance is validated.

9. Maintain explicit active/inactive lifecycle state.

10. Prevent deleted memory from re-entering active retrieval.

11. Keep audit retention separate from active model memory.

12. Revalidate security-sensitive state from trusted systems
    whenever a sensitive decision occurs.

13. Measure proposal quality separately from security outcome.

14. Measure semantic memory fidelity in addition to successful
    persistence.

15. Log memory writes, sanitization, provenance, retrieval,
    deletion, and security decisions for auditability.

16. Use defense in depth rather than relying on model
    obedience.
