The register follows an evidence-first principle:



ACTIVITY



↓



ARTIFACT



↓



EVIDENCE



↓



CAPABILITY



↓



SECURITY RELEVANCE



↓



PROFESSIONAL CLAIM



## Evidence Integrity Principle



An artifact should only be recorded as verified evidence when the underlying file exists and can be inspected.



Evidence status will use the following classifications:



\- VERIFIED — artifact exists and has been inspected.

\- PRESENT — artifact exists but has not yet been fully reviewed.

\- PENDING — expected evidence has not yet been verified.

\- NOT APPLICABLE — no separate evidence artifact is required.

## Evidence Quality Criteria



Evidence should be evaluated according to:



### Relevance



Does the artifact demonstrate the claimed security capability?



### Authenticity



Was the artifact produced through the documented laboratory activity?



### Traceability



Can the artifact be connected to a specific lab, assessment, test, or finding?



### Reproducibility



Can the methodology or result be explained and, where appropriate, reproduced?



### Integrity



Has the artifact been preserved without misleading modification?



### Professional Value



Would the artifact help demonstrate capability to a recruiter, hiring manager, security engineer, auditor, or client?



## Evidence Strength Model



Evidence can be classified as:



### Level 1 — Documentation



Examples:



\- Markdown notes

\- Methodology documents

\- Learning summaries



### Level 2 — Technical Output



Examples:



\- Console output

\- JSON / JSONL results

\- Test logs

\- Scanner output

\- Model responses



### Level 3 — Reproducible Security Evidence



Examples:



\- Documented attack procedure

\- Input and output pair

\- Reproduction steps

\- Finding with supporting logs

\- Before-and-after remediation test



### Level 4 — Professional Assessment Evidence



Examples:



\- Security assessment report

\- Risk-rated finding

\- Executive summary

\- Remediation recommendation

\- Retest evidence

\- Detection or control mapping



The strongest portfolio should contain a mixture of Levels 2–4 rather than relying only on documentation.



## Evidence Handling Rules



The portfolio must not expose:



\- API keys

\- Authentication tokens

\- Passwords

\- Private credentials

\- Sensitive personal information

\- Proprietary data

\- Unauthorized target information

\- Secrets contained in logs or configuration files



Artifacts intended for GitHub publication should be reviewed and sanitized before being committed.



## Evidence-to-Claim Rule



No professional claim should exceed the strength of its supporting evidence.



For example:



Weak evidence:



Reading about prompt injection.



Permitted claim:



Studied prompt-injection attack concepts and mitigation approaches.



Stronger evidence:



Executed controlled prompt-injection tests and preserved input/output evidence.



Permitted claim:



Performed controlled prompt-injection security testing and analyzed model behavior under adversarial instructions.



Professional assessment evidence:



Documented reproducible prompt-injection findings, risk, remediation, and retesting.



Permitted claim:



Conducted structured LLM prompt-injection assessments, documented reproducible security findings, evaluated impact, and recommended remediation.
